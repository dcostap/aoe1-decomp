# 004DC750 objectToAttack: ordered score repair

## Decision

Approve the ordered integer score additions as a partial source repair.
Keep the function in `scratch`. This review does not establish whole-function equality.
The shared protected-array proposal remains separate.

## Original evidence

Original `004DCCE9..004DCE5B` contains 85 score instructions and 14 getter calls.
The executable calls `TribeTacticalAIModule::strategicNumber` in this order:

`59, 90, 7B, 7A, 50, 53, 4D, 6F, 5A, 4E, 4F, 52, 6E, 6D`.

Each number above is hexadecimal.
The executable multiplies each returned integer by its term and accumulates the results in that order.
It reloads the main-module pointer before each getter call.

Original `004F6210` performs a read-only, signed bounds check and integer lookup.
It accepts indices from zero through `0xE1`. It returns `-1` outside that range.
Call counts alone cannot establish the required indices, pointer reads, or accumulation order.

## Repair

The previous long sum left operand evaluation order unspecified.
Its getter order changed with the compiler inputs, including the protected-array proposal.
Initialize `rating` with the first product. Use one `rating += ...` statement for each remaining product.

The rebuilt score region is `004DCCFD..004DCE6F`.
All 85 operations agree with the original after direct-target resolution and two private-home mappings:

| Value | Original stack offset | Rebuilt stack offset |
| --- | --- | --- |
| `specialRating2` | `0x3C` | `0x40` |
| `typeMatchB` | `0x40` | `0x64` |

The earlier assignments identify those homes. The mapping does not merge distinct values or change their widths.
The comparison preserves every pointer read, push, multiply, addition, and register operation in this region.
It checks all 14 call relocations against the owning getter symbol.
It does not mask other instruction differences.

The machine operations retain the original low 32-bit multiplication and addition results.
The region introduces no floating-point operation, allocation, write through a caller pointer, or exception handler.
It restores the original order for pointer-read faults and getter calls.
Caller-owned overlap remains in scope. Fabricated pointers into future private stack storage do not.

## Limits

This repair does not approve the complete function, its layouts, or all earlier arithmetic and fault paths.
The complete result remains `MISMATCH`:

- Original: 1,977 bytes. Rebuilt: 2,008 bytes.

The main and protected builds now emit identical descriptions for this complete owner.
That agreement resolves this owner's shared-header difference. It does not replace comparison with the executable.

## Broader semantic review, 2026-09-10

### Decision

Keep `004DC750` at status `scratch`. Do not promote it to `matching` or
`accepted_drift`. No source or registry change is supported by this review.

### Behavior

The original body is a `__thiscall` `ObjectMemory*` return with an `int&`
output parameter. It first calls `wonderToAttack(-1)`. A non-null result sets
the output to `1` and returns. A null unit or null initial `unitAI()` returns
null without changing the output. The current source keeps this order.

The loop scans `maxImportantObjectMemory` records. The proven record size is
`0x24`. The original initializes a byte cursor and an integer record counter
only after the positive-count guard. Every path advances both by one record at
the shared tail at `004DCECB`. The source reads owner, ID, type, coordinates,
hit points, kills, damage, rate, and range from the same record offsets.
It does not use `ManagedArray` count fields for this raw object-memory array.

The owner filter, object lookup, null check, and unsigned `object_state <= 2`
check occur in the original order. The source then preserves the damage and
rate calls before the siege, boat, conversion, and visibility filters. The
conversion call uses the current record ID and virtual slot `+0xC4`.
The visibility test uses candidate coordinates. The later distance and zone
tests use the memory coordinates and the unit or candidate as in the original.

The integer divisions retain the original field widths: signed `id`, hit
points, and short memory hit points; unsigned-byte kills; and float damage,
rate, and range. Zero tests guard the integer divisions. The x87 comparisons
and conversion calls retain the original NaN and signed-zero machine behavior
in the rebuilt assembly.

The random call at `004DCBB8` occurs before the three type comparisons. The
strategic-number getter order is `59, 90, 7B, 7A, 50, 53, 4D, 6F, 5A, 4E,
4F, 52, 6E, 6D`. The current ordered additions preserve this order and the
low-32-bit multiply and add operations. First-best selection, strict score
comparison, `rating = 1` override, and output publication match the original.

On a null or empty scan, the return is null and the incoming output value is
unchanged. A selected record writes `1` to the caller output and returns the
record address. The candidate pointer remains live across the same calls and
the source reads its coordinates and master record at the same later points.
The private extra cursor stores in the rebuild do not point into game memory.

The static review found no changed game-memory write, call reorder, direct-call
target change, or virtual argument change. It did not execute the game or a
runtime harness. Dynamic virtual overrides, caller-created output aliases, and
malformed object-memory pointers therefore remain untested.

### Source

`src/taiinfmd.cpp` remains the natural PDB owner. The source has no wrapper,
inline assembly, fixed address, fake helper, or dummy ABI. The PDB packet names
the byte-offset loop local, output parameter, unit, best pointer, and rating
locals. The `ObjectMemory` layout and the `findObjectMemoryLimits` struct-return
ABI are reviewed layouts. The raw cursor spelling is supported by the PDB
byte-offset local and the original `add 0x24` tail; it is not a new compiler
steering probe.

The remaining semantic gap is not a known normal-input defect. The source has
not proved all behavior for aliases that let the caller output overlap the
object-memory array, or for virtual calls that mutate those records. Static
call and fault-order review shows the same operation order for the ordinary
valid-object path, but the current evidence does not support an all-input
accepted-drift claim.

### Bytes

The final target check used source hash
`b93e5ac7fe13535a82ad579c34063bbf1b7b574930f81482bd0dd2970956dd87`.
It reports original `1977` bytes and rebuilt `2008` bytes, `1419` differing
bytes, a `0x88` frame on both sides, four saved registers on both sides, and
`44/44` aligned calls. Ownership matches. The first strict mismatch is
`004DC784` (`+0x34`). The rebuilt body extends beyond the original boundary,
so the check reports a boundary problem. CFG signals are `57/57`, but the
checker reports eleven attributed edge or terminator differences and four
extra rebuilt instructions. This is not positional exactness.

The one-job `taiinfmd` audit used fingerprint
`c73db4694c3411eff002c337998d9213d4c282bdc267c04a39e78eb64cec1c1a`.
It compiled all 121 normal owners. It reported 98 matching results, eight
accepted-drift observations, seven boundary problems, five grouped mismatches,
and three relocation problems. No exact neighbor regressed. The target stayed
at `1419` differences.

The mismatch is broad register, local-home, and control-flow code generation,
not a narrow encoding difference. The target check also reports a high
structural control-flow difference. This does not meet the accepted-drift
standard for a narrow explained drift with complete fault and alias proof.

### Integration

No source, header, registry, or candidate patch change is proposed. Keep the
registry entry and the ordered score repair as they are. Preserve the target
check at `build/history/004DC750_objectToAttack/runs/20260910T154506.440372Z-b93e5ac7fe13535a82ad579c34063bbf1b7b574930f81482bd0dd2970956dd87` and
the closure report under `build/sa-a5947210-taiinfmd-audit/`.

Exact matching needs a new source or compiler-context explanation for the
`+0x34` register and local-home basin, plus a source that stays within the
original boundary. Accepted drift needs independent proof for output aliases,
virtual-call mutation, exceptional paths, and the broad CFG difference. Until
that evidence exists, the correct result is an unresolved scratch function.
