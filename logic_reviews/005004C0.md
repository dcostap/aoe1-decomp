## Concrete fault-order difference

Choose distinct page boundaries P and Q.
Map page P but not its preceding page.
Map the page preceding Q but not page Q.

Set the first list node H to `Q-0x1C4`.
Its next pointer at `H+4` and type at `H+0x14` are readable.
Give H a type other than the requested type 106.
Set its next pointer to node T at `P-0x14`.

Node T has a readable type at P; set it to 106.
Its action field also lies in mapped page P, if the action filter needs it.
Its id at `P-8` is unreadable.
H's assistGroupID at Q is unreadable.

The outer search skips H because its type differs, then reaches T.
The inner search starts at H.
Both pointers pass their nonnull and sentinel checks.
The original first faults reading T's id at `P-8`.
The rebuild first faults reading H's assistGroupID at Q.

This is a constructed instruction-level counterexample, not a claimed executed test.
It explains why the preceding-read proof for `004D4F80` does not apply here.

### Concrete input

Let S denote entry ESP. Set `point = S - 0x14`.
This points into the callee's future local storage, not an ordinary live C++ object.
This review applies the retained malformed-input and stack-overlap requirement to that case.

Use these remaining values:

- `this = 0x20000000`.
- One group at `0x30000000`; its next pointer equals `this + 0x9D4`.
- The group's gather coordinates are both zero.
- `type = action = zone = -1`; the distance limit is 2.
- All accessed memory is mapped, with required writes permitted.
- The x87 stack starts empty with its default control word.

Both prologues place the frame base at `S - 0x24`.
Thus `point.x` occupies frame offset `+0x10`; `point.y` occupies `+0x14`.

| Body | `point.x` after initialization | `point.y` after initialization |
| --- | --- | --- |
| Original | `this`, or `0x20000000` | Initial best distance, or `-1` |
| Candidate | Initial best distance, or `-1` | List sentinel, or `0x200009D4` |

The disabled filters skip type, action, assist, and zone processing.
Both bodies then read these overwritten point coordinates in their distance calculation.
The gather getter only returns `group + 0x19C`.
The conversion helper writes below the caller's frame base, outside these two point words.

The x86 integer products and sum keep their low 32 bits:

- Original: `(0x20000000 squared + 1) mod 2^32 = 1`.
- Candidate: `(1 + 0x200009D4 squared) mod 2^32 = 6,330,257`.

Both signed results are positive. Square root and truncation produce 1 and 2516, respectively.
The original selects the group because 1 is less than 2.
The candidate rejects the group because 2516 is not less than 2.
Both then reach the sentinel. The original returns `0x30000000`; the candidate returns null.
