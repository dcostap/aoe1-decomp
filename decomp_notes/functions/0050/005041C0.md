# Function notes: 005041C0 `TribeElephantUnitAIModule::processNotify`

Module notes: `decomp_notes/taiuaimd.md`.

## Behavior

The original body is `005041C0-005042C4` (261 bytes), with `__thiscall`
ABI and PDB source `taiuaimd.cpp:274-317`. The PDB names the parameters as
`NotifyEvent* nEvent` at entry `+0x4`, and `unsigned long uTime` at `+0x8`.

The original reads `event->mType` at `+0x8` first. Type `0x20F` returns `2`
without another effect. Other types call `UnitAIModule::processNotify(event,
param_2)` and return its result.

For type `0x1F4`, signed `event->p2 <= 0` calls
`purgeNotifyQueue(param_2)` and returns `4`. For a positive `p2`, the function
reads `event->caller`, scans `attackingUnitsValue` (`value` at `this+0x60`,
`number` at `this+0x64`, and `capacity` at `this+0x6C`), and suppresses a
duplicate caller.

If the list is full (`number > capacity - 1`), it allocates
`(number + 1) * 4` bytes, copies up to the old capacity, deletes the old list,
and publishes the new pointer and capacity. A failed allocation does not skip
the original insertion. The caller is written at the current number and the
number is incremented. The original then calls `objectValue->setUnderAttack(1)`,
`closestAttacker(0)`, and `attackObject(result, 0)`, in that order, then returns
`3`.

The observed fault order is therefore event read, `p2` test, purge on the
failure path, caller read, bounded scan, allocation, copy, delete, publication,
insertion, count update, and the three final virtual calls. No runtime input
test was available; this review uses the original executable listing and exact
rebuilt bytes.
