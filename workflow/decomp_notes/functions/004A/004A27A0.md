# 004A27A0 `calcRandomPositions`

## Behavior

I reopened this accepted-drift target and traced the original body. It counts human and computer players. It rechecks `numberPlayers()` after each count. It initializes eight scenario slots from dropdown lines. A `-1` line marks a slot unavailable; other lines mark it free.

If active players do not exceed free slots, the function visits player indexes from zero. It stores the next one-based player value in `position_used[0]`. It assigns only humanity values 2 and 4. For each active player, it scans `scenarioPlayerCount` entries from `position_used[1]`. It then tries up to 1,000 random positions. The signed product is divided by `0x7fff`, then clamped to `[0, count - 1]` in the original order. The function calls `setScenarioPlayer(player, selected_position)` before it stores the player in the chosen slot.

The eight slots use indexes 1 through 8. The original also uses index 0 for the next player. The PDB listing labels `position_used` as `int[8]`, but the original accesses a ninth stack dword. Do not remove this effect. Runtime boundary tests did not run.

## Source

`src/scr_mps.cpp::TribeMPSetupScreen::calcRandomPositions` remains unchanged. Its nine-dword buffer models the original next-player value at index 0 and the eight position slots at indexes 1 through 8.

I tested smaller array forms. An eight-element array without a separate next-player local shrank the frame from `0x2c` to `0x28`. Its unchanged stack-relative initialization then wrote slot 8 at entry `ESP+0`, the caller return-address slot. Adding a separate `next_player` restored the frame but produced a 374-byte body and about 230 differing bytes. The smaller forms are rejected.
