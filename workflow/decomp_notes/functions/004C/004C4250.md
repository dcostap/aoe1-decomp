## Behavior

The original accepts one `long` object ID and uses `__thiscall`. A negative ID
returns null. A non-negative ID is searched in this order:

1. The owner player's `objects` list.
2. The owner player's `sleeping_objects` list.
3. The owner player's `doppleganger_objects` list.
4. Each other world player, in player-index order, across the same three lists.

Each list uses the direct `RGE_Object_List::find_by_id(long)` call. The first
non-null result returns. The function returns null after all six list roles fail.

The original instructions prove these field accesses:

- `RGE_Static_Object::owner` at `+0x0C`.
- `RGE_Player::objects`, `sleeping_objects`, and `doppleganger_objects` at
  `+0x28`, `+0x2C`, and `+0x30`.
- `RGE_Player::world` at `+0x3C`.
- `RGE_Game_World::player_num` at `+0x3C`.
- `RGE_Game_World::players` at `+0x40`.
- `RGE_Player::id` at `+0x4A`.

The world count is checked as a signed word. The player ID comparison is a word
comparison. The loop starts at index zero, skips the owner ID, and tests the
count again after each complete three-list pass.

The six calls align with the same direct `find_by_id` target. The callee only
reads the list, node, and object ID fields. It does not alter the owner, world,
list, or ID values used by this function. No runtime test was run because this
repository does not permit an executable test for this target.

## Source

The source in `src/stat_obj.cpp:1528-1572` follows the proven control flow. The
`object_id` local preserves the incoming ID before the player scan. The
`player_index` local is an `unsigned char`. The `compare_index` local is a
`short`, which produces the proven signed word loop condition.

The source has two important compiler aliases:

- `EBP` carries the incoming `id` and remains the saved `object_id` used by all
  six calls.
- The low byte of the incoming argument home at `[esp+0x14]` carries the
  `player_index` spill. The original PDB calls the stack symbols `obj_id` and
  `player_id`; this does not prove a distinct source object for the spill.

The original uses `ESI` for the owner pointer before the loop and for the player
index during each pass. It uses `EDX` for the word compare index. The rebuilt
source uses `EDX` for the owner pointer and `ESI` for the word compare index.
Both forms use `BL` for the byte index and reload the owner before the tail.
These are register and lifetime aliases, not different list roles.

## Fault order and accepted-drift decision

The register aliases do not reorder the six normal list calls or their memory
accesses. They do change machine state at exceptions. The tail also changes
memory-access order:

- The original writes the player index to `[esp+0x14]` before it reads
  `owner->world` at `004C4319`.
- The rebuilt code reads `owner->world` at `004C4316` before it writes
  `[esp+0x14]` at `004C4319`.
- The original writes `BL` into `DX` after the owner-world load. The rebuilt
  code writes the new index into `SI` before that load.
- If the owner-world load faults, the original has changed the argument home
  and cleared `DX`; the rebuilt code has not changed the home and has set `SI`.
- If the argument-home store faults, the original has not read `owner->world`;
  the rebuilt code has already read it.
- If the world count read faults, both have stored the index, but the index is
  in `DX` in the original and `SI` in the rebuilt code.

The initial world-count block and all body dereference sequences keep the same
memory order. Their register colors still change exception register state.
The tail memory and fault-order differences are not a narrow encoding-only
difference. They prevent a strict accepted-drift proof, even though normal
successful calls return the same object for the same stable object graph.

No supported natural repair reaches the original register and store schedule.
Do not add volatile accesses, inline assembly, wrappers, or artificial aliases.
Keep the current source until new period-source or compiler evidence appears.
