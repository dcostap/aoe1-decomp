#### Behavior

The original executable remains the oracle. The fresh dossier records the PDB
locals, 42 call sites, object offsets, stack accesses, and DirectSound slots.
The target packet has no `PdbScopedSymbols` heading. The dossier supplies that
section: `file_name`, `res_id`, `buffer_desc`, `wave_hdr`, `load_type`,

The function entry tests `failed`, delegates to `owner->load(file_name, -1)`,
checks `sound_system`, logs, unloads an existing load, and copies at most 12
filename bytes. The effective resource id uses signed `<= -1`. File loading
runs when `sound_file_first` is nonzero or the effective id is negative.
The file path opens read-only, reads 44 header bytes, accepts any nonzero
unsigned read result, checks `RIFF` and format tag 1, then allocates and reads
the data. Zero reads fail; short positive reads do not. A read result of
`-1` also follows the success branch because the result is unsigned.

The resource path rejects ids `<= -1`, calls `RESFILE_load` with the wave type
and two output references, copies 44 header bytes, and allocates the wave data
using `resDataSize`. `load_type == 1` owns the returned resource buffer.

fails with `load_type == 1`, the executable frees that same pointer again.

`wave_data`; successful resource loads keep it for later unload. These are
original cleanup effects, not repairs to make here.

`size1` bytes from `wave_data`; it copies the second segment only when `size2`
is nonzero, from `wave_data + size1`. Unlock receives the same two pointers and
two sizes. On Lock failure the source releases the buffer before it clears the
member, as the executable does.
