# 0050D5B0 RGE_Timeline constructor

## Behavior review

The original function is 471 bytes. The packet is `inventory/functions/0050/0050D5B0_RGE_Timeline.txt`.
It shows the original instructions and source-line map. The body starts at `0050D5B0` and returns at `0050D784`.
The symbol is `??0RGE_Timeline@@QAE@HPAVRGE_Game_World@@@Z`. PDB names the owner `Timeline.cpp`.

The constructor uses `__thiscall`. It receives `infile` as an `int` and `gworld` as `RGE_Game_World*`.
PDB scoped symbols name `index` as `long` and both saved player IDs as `short`.
The reported PDB stack offsets overlap parameter homes and conflict with the raw read destinations.
Use the instructions to resolve each live stack address. The binary writes target-player ID to entry argument home +4,
then writes this-player ID to a local at entry ESP -0xE.

At `0050D5C7`, the function writes the timeline vtable to `this+0`.
It reads `list_num` at `this+0xC` (2 bytes), `avail_id` at `this+0xE` (2 bytes), then `old_time` at `this+0x10` (4 bytes).
Each `rge_read` gets `(infile, destination, size)` and the caller removes 12 argument bytes.
At `0050D602`, it stores `gworld` at `this+4`. It clears `time_list` at `this+8`.

The signed 16-bit `list_num` controls the loop. Values at or below zero skip all entry work.
A positive count allocates one zeroed 0x30-byte entry per iteration with `calloc(1, 0x30)`.
There is no allocation check. The event reads use this order: time +0/4, command +4/1, object type +6/2,
player +8/1, X +0xC/4, and Y +0x10/4.
Then read Z +0x14/4, task +0x18/2, and this-object ID +0x20/2.
Then read target-player ID into the `infile` home, target-object ID at entry +0x28, and this-player ID into a stack local.
The event input record is 30 bytes. Zeroed padding remains in the 48-byte entry.

At `0050D6B0`, the target-player read writes two bytes to the incoming `infile` stack home.
The function saved `infile` in `EDI` at `0050D5B8`, so later reads still use the original handle.
At `0050D6DC`, it reads the overwritten low word as signed `target_player_id`.
The final two-byte read writes the signed `this_player_id` local at `0050D6CF`.
The PDB variable names and types support these IDs. The machine instructions prove the live addresses.

At `0050D6E4`, a negative target-player ID skips the first lookup.
A nonnegative ID and non-null world select `world->players[target_player_id]->objects`.
The instruction reads `players` at world +0x40 and `objects` at player +0x28.
The local headers and type dumps support these offsets. The function does not read `player_num` at world +0x3C.
The first `find_by_id` call at `0050D704` gets the signed 16-bit `this_obj_id`, extended to `long`.
Otherwise, the constructor stores null at entry +0x1C.
There is no player-array, player-pointer, or object-list null check.

At `0050D715`, a negative `this_player_id` skips the second lookup.
A nonnegative ID and non-null world enter it. The index is `target_player_id`, not `this_player_id`.
The `find_by_id` call at `0050D73B` gets signed `target_obj_id`, extended to `long`.
Otherwise, the constructor stores null at entry +0x24.
This is an original bug. The second lookup tests `this_player_id` but indexes with `target_player_id`.
It can index outside the player array. Preserve this fault risk.

Each `find_by_id` call uses `__thiscall`. The object list is in `ECX`.
One signed 32-bit ID is on the stack.
The callee at `00463490` walks its node list and returns the matching object or null.
The callee returns with `ret 4`. The constructor does not check either lookup result.

The tail pointer starts at `&this->time_list`. Each iteration saves the current link address.
It sets the next tail to `&entry->next` and clears `entry->next`.
Then it links the entry through the saved address.
The loop increments a 32-bit index and compares it as signed against the sign-extended 16-bit count.
It preserves serialized order. It does not change `list_num` after the header read.
For positive counts up to 32767, the index does not overflow.

The constructor does not check `rge_read` results. The callee at `00480080` can return without writing when the handle is invalid.
The constructor then uses zeroed entry fields and may read an unwritten stack ID. This path is not runtime-tested.
Bad player indices, null player entries, null object lists, truncated input, allocation failure, and invalid handles were not runtime-tested.
The instruction order shows the fault order. Header reads and field writes come first.
Then come allocation, event reads, lookups, link writes, and the loop test.

At `0050D784`, the constructor returns `this` in `EAX` and uses `ret 8`.
It restores `EBX`, `ESI`, and `EDI`; it also restores `EBP` when the positive-count loop pushed it.
The target has no exception handler or explicit cleanup path.
