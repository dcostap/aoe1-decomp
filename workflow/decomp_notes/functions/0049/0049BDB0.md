### Behavior

Oracle: local `XPack/empiresx.exe`, SHA-256
`88a0392120280c1b91ee90fe6f7cf50c72e55149a16c9b1ca79505572b8b9c90`.
I disassembled VA `0049BDB0-0049BE90` with `llvm-objdump`.

- At `0049BDBA-0049BDC7`, it gets pause state and exits when nonzero.
- At `0049BDCD-0049BDF4`, it reads the command id, gets the player, checks
  cost with `&attr`, `1.0f`, and the saved pause value, then branches on AL.
- At `0049BDF6-0049BDFB`, success stores SI to `[game+0x3FC]`. This is a
  16-bit store. It then gets the player again at `0049BE02`.
- At `0049BE0D-0049BE21`, it indexes `master_objects[id]` and tests byte
  `[object+0x16C]`. The true branch calls virtual slot `+0x10` with `0x15` at
  `0049BE23-0049BE29`. The false branch uses the same slot with `7` at
  `0049BE37-0049BE3D`.
- On cost failure, `0049BE4B-0049BE67` calls virtual slot `+0x28` with string
  id `0x67`, domain `1`, signed `attr`, a 512-byte buffer, and length `0x200`.
  `0049BE6A-0049BE81` calls `show_message` with type `0x56` and the buffer.

The current source preserves these branches, widths, values, and calls. The
rebuilt call alignment is 8/8. One ordering difference remains: the rebuild
loads `message_panel` before argument pushes. The executable loads it after
the pushes and before the final `1` push. This is a compiler scheduling
difference for a valid screen and stack. Fault order for invalid `this` or a
