# Logic review: 00421110 `RGE_Base_Game::handle_mouse_move`

## Revoked approval and exact repair, 2026-09-06

The old accepted-drift approval below is invalid. It missed a write to the return address.

### Behavior

CDB reproduced the title-screen crash with and without startup videos.
The failing message was `WM_MOUSEMOVE`, with coordinates `(320, 240)`.
A hardware write breakpoint caught `get_mouse_info` replacing the caller's return address with `0xF0`.
The return slot at `001AE674` changed from `0041C788` to `000000F0`.
The writing instruction was rebuilt `0041BF09`: `mov [edx+4],ecx`.
The process later attempted to execute `0xF0`.

The original reserves 24 local bytes and saves two registers on the ready path.
Let S denote ESP after those operations. Its return address is at `S+0x20`.
The complete `POINT` occupies `S+0x18` through `S+0x1F`.
The four flag outputs occupy `S+0x14`, `S+0x10`, `S+0x0C`, and `S+0x08`.
The six action arguments are X, Y, left button, right button, control, and shift.
No argument requires an uninitialized local.

The old source passed `&point.y` as a complete `POINT` reference.
Its 20-byte frame placed the return address at `S+0x1C`.
Thus, the second coordinate write replaced that return address.
The ignored action argument did not make this memory write safe.

An original-runtime control reached the handler return with valid return address `00420C5A`.
It used the same mouse coordinates, `NOSTARTUP`, and process-local compatibility setting.

### Source

It passes their initialized values to `action_mouse_move` in the original order.
The PDB records support `tagPOINT point` and separate left, right, control, and shift locals.
No aggregate layout carrier, interior pointer, volatile value, or assembly is required.
