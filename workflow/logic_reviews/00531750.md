# Logic review: 00531750 `RGE_Victory_Conditions`

Current source: `src/victory.cpp`.

## Behavior

The original body range is `00531750-00531AE7`. The rebuilt body keeps the
same reachable paths and has no boundary escape. Both bodies implement the
four-argument `__thiscall` constructor and return the constructed object.

The header path is equal. The constructor reads the optional save version,
the entry count, and the victory byte. It stores the player pointer and clears
the victory-list head before the entry loop.

Each entry allocation uses `calloc(1, 0x34)`. Each entry then receives the same
14 serialized fields, in the same order and widths. The constructor clears
`target_obj`, `this_obj`, and `target_player`, links the entry at the list tail,
and increments the same loop counter.

For a nonnegative serialized object ID, both bodies scan every world player.
They read the same world player count and object-list pointer. They call
`find_by_id` with the same ID and stop on the first result. A failed scan sets
the entry state to `3`.

Both bodies resolve the direct target object when its ID is nonnegative. They
then apply the optional version map. A negative mapped version sets state `3`.
Otherwise both read the same world player array, store the same target player,
and perform the same mapped target-object lookup when required.

The final target-ID check sets state `3` when the target remains unresolved.
Negative IDs skip their lookup paths. Negative versions clear the target-player
field. These predicates preserve signed 32-bit behavior for every bit pattern.

Both bodies clear the point-list head and count. For save versions at least
`1.0`, both read the total and point count, allocate each `0x1C` point entry,
and read the same nine point fields. Negative total points clamp each point's
`points` field and the final total to zero. Older save versions set the total
to zero.

The direct call sequence is equal. The 33 static call sites target only
`rge_read` at `00480080`, `calloc` at `0054B730`, `find_by_id` at `00463490`,
and `add_point` at `00532F50`. No target call is virtual. All call arguments,
widths, receiver values, and cleanup agree.

Allocation failure has equal behavior. The entry allocation has no null check
in the original or source, so the following `rge_read` receives the same null
pointer. The point allocation has the same behavior. The caller's outer
allocation failure path is unchanged.

The only receiver setup reorder is the private `target_object_id` push before
one direct object-list load. The push writes callee-owned stack storage. It has
no caller-visible effect and cannot fault with a valid stack. Both versions
fault at the same receiver dereference for an invalid object graph, before any
external call or later object write. The supported `load_victory` caller passes
a valid player object. Direct construction with invalid object pointers is not
a supported game contract.

No call or callback occurs between any changed field stores. The early
list-count load and player store address distinct fields in a valid
`RGE_Victory_Conditions` object. The changed `test` and `cmp` forms feed only
the same signed-less-than branch. They produce the same branch result.

The constructor has no local object with a destructor and no local cleanup
handler. A fault during a read, allocation, or lookup therefore leaves the
same partial object state and cleanup obligations. The unchanged caller keeps
the original exception registration and outer allocation cleanup.

Runtime tests were not run. The review uses static original evidence and pinned
compiler artifacts, as required by repository policy.
